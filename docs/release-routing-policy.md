# 发布方式选择：小规模默认局部发布，大规模才全站构建

用户确定的默认规则（2026-10-07）：先评估小规模流程，不默认触发全站
production build。Mac完整production build始终不是常规发布前提。

| 改动 | 默认方式 | 构建范围 |
| --- | --- | --- |
| 已有zone内兼容文字/场景配置 | 运行时内容包 A | 不build、不restart |
| 一两个页面布局/组件、少量学校、白名单/schema扩展 | 有界页面服务 B | 只build该zone |
| 少量月报变更，但尚未接入运行时loader | 先做有界月报适配/试点 B | 不能假装已免build；不默认全站生成 |
| 全站共享布局、框架/依赖、全站语言或路由策略、广泛API/数据契约变化 | 大版本发布 | OCI一次权威全站build |

小规模的判断是影响范围和兼容性，不是简单按文件数/学校数。
十校批量已经验证可使用一个有界zone；一行共享布局也可能影响全站。
如果小规模路径不适用，先说明具体技术依赖及影响范围，再采用大版本
流程；不得在未分析时自动跑`@uapt/web build`。

- 小规模命令与验收权威：[OCI small release](oci-small-release.md)。
- 大规模命令与验收权威：[OCI build-once release](oci-build-once-release.md)。
- 审核、原文/数据契约、候选验收、精确影响范围、旧artifact回滚在两条
  流程都保留。发布授权不会因为“无build”而自动扩大。
- 大版本切换要核对已有zone仍然覆盖哪些路径；共享数据/组件变化必须
  协调升级zone或明确取消覆盖。只更新主站不等于所有zone也更新了。

当前小规模生产证据：70路由、420候选浏览器状态、89展示记录；十校
小build13个基础静态项。它证明当前有界方式可行，不等于任意页面/数据
都已经成为运行时内容，也不构成高并发性能承诺。

本规则替代旧文档“每次发布必须全站build”的表述，历史报告保留原始
结果。修改文档本身不授权build、push、服务重启、切流量或索引通知。

## 2026-10-16 必须通过的生命周期门禁

快速发布还必须遵守 [服务生命周期与容量门禁](release-lifecycle.md)。保留旧 artifact 不等于保留旧进程；固定槽位、容量检查、持久化切换恢复、静态资源迁移和旧 active 退役都是完成条件。禁止继续运行按版本创建常驻服务的一次性 cutover 脚本。事故遗留动态依赖只允许登记并逐项迁移，不得随发布扩张。
